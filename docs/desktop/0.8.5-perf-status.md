## Where the numbers come from

  Synthetic CT from `scripts/make-test-ct.py --slices 848`, the same file CI uses.
  The CI arguments were used, with the Windows limits (the strictest).
  - On Linux the native (wgpu) renderer is off by default, and `FLOWRAD_NATIVE=1` still
    renders with the JS engine (`render gpu`) under Xvfb. So the Linux open, interaction,
    idle-2D, close and leak numbers measure the **JS / WebGL path on a software GPU**.
    The macOS and Windows gates measure the native path. Read the Linux memory and
    frame-time numbers as a different path, not as a forecast for macOS or Windows.
  - "Before" is integration `5e0d17d`. "After" is this branch, which adds cold-start
    diagnostics only (see [Changes](#changes-on-this-branch)).
- **macOS CI.** Hosted `macos-latest` runner, last runs before Actions were switched to

- **Windows CI.** `perf-windows`, [run 42246615159](https://github.com/drskatyal/Radiologytutor/actions/runs/42246615159)

## Cold start: where the time goes

`appMs` = `windowBuiltMs` + (page first paint − Rust's "page load started"). The webview's
own start-up (WebKitGTK about 580 ms here, WebView2 about 450 ms, WKWebView 1.3–1.9 s on the
macOS runner) is not counted.

**Rust before the window (Linux, final build, 5 runs).**
- Everything in `run()` before `Builder::build()` (context, launch args, bench threads,
  state): 0.6 ms.
- `Builder::build()`: 55–77 ms. To find where it goes, the instrumented build added marker
  plugins between FlowRad's three plugins. Plugin and state set-up took under 0.1 ms in
  total, so the whole of `build()` is the runtime's own start-up: tao/GTK, GLX probing on
  llvmpipe and D-Bus autolaunch attempts (from `strace`).
- That start-up is platform code. Its macOS counterpart (AppKit) is what took 72–142 ms
  on the CI runners.
- No FlowRad code on this path can be moved off it for all platforms.

**The page (shared bundle).** Times are ms from the webview's navigation start.

| | page HTML received | first paint | entry script running | DOMContentLoaded |
|---|---|---|---|---|
| Linux (this branch) | 16–23 | 23–31 | 63–93 | 68–101 |
| Windows CI (`289cbc4`) | 20–26 | 44–64 | — | 81–96 |
| macOS CI (#180 runs) | 72–101 | 136–172 | — | 228–279 |

- On Linux the first paint comes before the entry script runs. The 649 kB entry chunk is
  not on the paint's path, and the page's share is about 10 ms.
- The same bundle and the same Tauri asset code take 4–5× as long to deliver the HTML on
  the macOS runner, and 10× as long from the HTML to the first paint.
- About 140 ms of macOS's 205–231 ms share is page-side and specific to WKWebView or its
  scheme handler. The rest is the window build.
- Linux cannot show a platform-independent change that would shorten it, so none ships
  (step 4 of the brief).
- Candidates that were measured or traced and rejected:
  - Plugin and state work in `build()`: under 0.1 ms.
  - Tauri's injected init scripts: the dialog plugin's 0.4 kB, plus core.
  - HTML CSP processing: string replace, no parse.
  - The tokio runtime start for the first asset request: sub-millisecond.

**Diagnostics added for the next macOS run.** The cold-start bench now prints a `rust:` line:
- when Rust handed over the page HTML and the entry script;
- Rust's "page load started";
- the page's first paint.

All are on the process clock. The `page:` line now includes "entry script running".
On macOS these lines show whether the 72–101 ms before the HTML arrives is spent in
Rust (asset serving) or in WebKit (scheme-task dispatch and delivery). It also shows
whether the first paint waits for the entry script. Linux example (final build, run 1):

```
page: html 18 · … · entry script running 65 · DOMContentLoaded 70 · load 72 · first paint 24 ms
rust: page html served 645 · page load started 655 · entry script served 662 · page first paint 664 ms
```

## Close memory: the macOS delta, and what Linux can and cannot say

- **macOS (16 / 20 MB, limit 30).**
  - The app process gives back nearly everything: open 57–60 → closed 34, against a
    29–30 MB empty app.
  - The WebContent process gives back nothing: open 53–54 → closed 54–55, against a
    39–43 MB empty app. Its +11–16 MB is the whole of the "flaky near the limit" margin.
  - It is page-side memory: the JS heap from the open, decoded preview and thumbnail
    images held by WebKit's memory cache, and DOM.
  - Windows' renderer gives back about half of its open growth (39 → 54 → 47).
- **Linux.**
  - The JS renderer is the default here, and its web process keeps about +170 MB after a
    close. It runs on a software GPU, which pulls in GL and WebGL state.
  - With identical code, the delta varied 147–186 MB between runs (4 runs of `5e0d17d`
    and this branch). This path is noisy too.
  - An experiment purged the Cornerstone cache, held volumes and idle decode workers on
    Home. Over 3 runs each it lowered the median delta from 181 to 171 MB, and the web
    process kept 298–302 MB against 307–312 MB.
  - That is inside the noise and not the main holder, so it did not ship.
  - The macOS WebContent growth is on the native path, which Linux cannot run here.
    It needs a macOS run with a WebKit memory breakdown (`footprint` categories are
    already printed by `bench.mjs close`).

## Reproducing the Linux numbers

```
(cd desktop && CARGO_TARGET_DIR=<shared target> npx tauri build --no-bundle)
python3 scripts/make-test-ct.py "$CT" --slices 848
xvfb-run -a node desktop/scripts/bench.mjs coldstart "$APP" --runs 5 --max-ms 900 --max-app-ms 150
xvfb-run -a node desktop/scripts/bench.mjs desktop "$APP" "$CT" --runs 3 --max-first-image-ms 1100 --max-first-visible-ms 400 --max-long-task-ms 150 --require-gpu
FLOWRAD_BENCH_VIEW=grid xvfb-run -a node desktop/scripts/bench.mjs mpr "$APP" "$CT" --settle 20 --max-settled-mb 400 --max-settled-private-mb 400
xvfb-run -a node desktop/scripts/bench.mjs close "$APP" "$CT" --settle 20 --after-close 30 --max-baseline-private-mb 240 --max-open-private-mb 400 --max-close-delta-mb 30
xvfb-run -a node desktop/scripts/bench.mjs interact "$APP" "$CT" --max-frame-p95-ms 33 --max-dropped 3 --max-interaction-ms 50
xvfb-run -a node desktop/scripts/bench.mjs leak "$APP" "$CT" --rounds 3 --max-leak-mb 400 --max-round-growth-mb 100
xvfb-run -a node desktop/scripts/bench.mjs mpr "$APP" "$CT" --max-ms 2000 --max-mb 1200
```

`desktop` run 1 drops the page cache, so it needs root.
